# i2i-search アーキテクチャ

ご要望の「意味で探す商品検索」（画像でもテキストでも、意味の近い商品を返す）を、我々はこう実装する。その方針と、それぞれがもたらす利点。

- デモ: https://i2i-search.cancer6.workers.dev
- リポジトリ: https://github.com/cancer/i2i-search

## 実装方針の全体像

1. 商品もクエリも**埋め込みベクトル**（意味を数値化した 768 次元の指紋）に変換し、ベクトル DB での近傍検索（cosine 類似度・topK）に一本化する
2. 埋め込みも商品説明文の生成も Google Gemini の API を採用する
3. 基盤はサーバーレス。検索 API・画面配信・ベクトル DB（Vectorize）を Cloudflare Workers の単一デプロイにまとめる

## 各方針の利点

### 1. 検索を 1 系統に一本化する

画像検索とテキスト検索を別々のエンジンとして作らず、「同一の埋め込みモデルで同一のベクトル空間に射影 → 近傍検索」の 1 系統で両方を実現する。

- **開発・保守の費用が 1 系統分で済む**。全文検索エンジンと画像類似エンジンを併設する構成と比べ、実装量も障害点も半分になる
- **機能追加が両方に同時に効く**。データ拡充や埋め込みモデルの更新が、画像・テキスト双方の検索精度に一度で反映される
- 比較可能性の要は「全ベクトルが同一モデル・同一次元」であること。埋め込みの生成はインデックス作成側・検索側で単一モジュールに集約し、モデルや次元がずれない構造にしてある
- 実測でも、テキスト「革のかばん」で商品名に「革」を含まない本革バッグが上位に出ることを確認済み

### 2. なぜ Gemini API か

埋め込み API の選択肢は複数あるが、次の理由で Gemini を採用する。

- **画像・テキスト・複合入力を単一の埋め込みモデル・単一の空間で扱える**。これが方針 1（1 系統化）の前提になる。検討時点で、主要な代替の埋め込み API の多く（例: OpenAI）はテキスト専用で、画像を同じ空間に載せられない。同じ Google でも Vertex AI のマルチモーダル埋め込みは廃止予定が出ており、新規採用に向かない
- **API キー 1 本でエッジから直接呼べる**。Vertex AI は OAuth トークンの発行基盤が必要になるのに対し、Gemini API はキーをヘッダに載せるだけで済み、実装が薄く納期が短い
- **埋め込みと説明文生成を同一プロバイダ・同一キーで賄える**。契約・鍵管理・課金の窓口が 1 つにまとまる
- **無料枠から検証を始められる**。デモ規模は無料枠内で稼働している

なお API 呼び出しは 1 モジュールに隔離してあり、モデルや提供元の変更が全体に波及しない（開発中、生成モデルの切り替えを定数 1 箇所の修正で完了した実績がある）。

### 3. サーバーレス基盤（Cloudflare Workers + Vectorize）

- **固定費がない**。検索 API・静的配信・ベクトル DB のすべてが従量制で、使われない時間の費用はほぼゼロ
- **増強・保守の作業が発生しない**。スケールは基盤側が自動で追従し、OS 更新や障害対応といった運用作業を持たない
- **構成が単純で障害点が少ない**。配信・処理・DB が同一事業者のマネージドサービスで完結し、デプロイ単位は Worker 1 つ。エッジ実行のため利用者から見た応答も速い

## 費用の構造

- かかるのは **AI API の従量課金**（埋め込み + 説明文生成）と**クラウド基盤の従量課金**のみ。固定費・ライセンス費はない
- デモ規模（商品 48 点）は双方の無料枠内で稼働している

## リスクと依存

- **外部 AI への依存**: 料金改定・仕様変更・レート制限の影響を受ける。緩和策は方針 2 の隔離構造と、レート制限（HTTP 429）への自動再試行。無料枠のレート制限が厳しいモデルは開発中に実測で検出し、軽量モデルへ切り替えて解決している
- **反映の時差**: ベクトル DB の更新は非同期反映のため、商品情報の更新から検索への反映まで数分かかる（デモ用途では支障ない）
- **完全一致の保証はない**: 近傍検索は「近いものを並べる」仕組み。型番検索など厳密一致が必要な検索は従来型を併用する

## 規模と育て方

- 数百点程度まではこのままの作りで足りる。数千点を超える段階では、絞り込み処理をベクトル DB 側（メタデータフィルタ）へ寄せる改修が最初の一手 — 作り直しではなく、同じ構成のまま部品を強化する形で育てられる
- ベクトル DB の次元上限（1536）に対し 768 次元を採用しており、モデル側の推奨値と DB 側の制約の両方に収まっている
- 検索結果の質は商品写真と説明文の質に比例する。実運用では商品撮影の統一が投資対効果の高いポイント
