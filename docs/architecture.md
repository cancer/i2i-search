# i2i-search アーキテクチャ

商品 DB に対する「意味で探す」検索のデモ。クエリは画像でもテキストでもよく、どちらも意味の近い商品を返す。

- 本番: https://i2i-search.cancer6.workers.dev
- リポジトリ: https://github.com/cancer/i2i-search

## この仕組みで何が変わるか

- **検索語のずれによる機会損失がなくなる**。従来の検索は商品名やタグと言葉が一致しないとヒットせず、「登録側が付けた言葉」と「探す側が使う言葉」のずれがそのまま取りこぼしになる。この仕組みは両者を「意味」に変換して照合するため、「革のかばん」で、商品名に「革」を含まない本革バッグが上位に出る
- **写真がそのまま検索語になる**。「これと似たものが欲しい」という言葉にしにくい要望を、店頭や SNS の写真 1 枚で受けられる
- **商品説明文を人が書かなくてよい**。各商品の紹介文は商品写真から AI が自動生成する。説明文は検索の材料にも使われるため、説明が付くほど検索が賢くなる状態を人手をかけずに維持できる。商品を入れ替えれば説明文も作り直される
- **従来型の絞り込みと共存する**。意味での検索に、価格帯・サイズ・色といったはっきりした条件を重ねられる

## 仕組みの考え方

- すべての商品を「写真 + 説明文」から作った意味の指紋（数値の並び）として、検索専用のデータベースに登録しておく
- 検索の入力（写真でも言葉でも）も同じ方法で指紋にし、指紋が近い商品を返す
- 画像検索とテキスト検索は入口が違うだけで中身は同じ 1 つの仕組み。検索を 2 系統作り分けないため、開発も保守も二重にならない

## なぜこの構成か（費用と運用）

- **サーバーを持たない**。検索処理・画面配信・データベースはすべてクラウドの従量制サービス（Cloudflare）上で動く。使われない時間の費用はほぼゼロで、デモ規模なら無料枠に収まる。アクセス増への増強作業や、OS 更新・障害対応といった保守作業が発生しない
- **AI は借りる**。意味への変換と説明文の生成は Google の AI（Gemini）を API として利用する。自前で AI を運用しないため初期投資が不要で、使った分だけの支払い。AI 側の性能向上の恩恵も自動的に受けられる
- **秘密情報の管理が単純**。AI を使うための鍵はクラウド側の secret 管理に 1 か所だけ置き、コードや画面には現れない。漏えいのリスク面積が小さい

## 規模と育て方

- 現在は商品 48 点で稼働。数百点程度まではこのままの作りで足りる
- 数千点を超える段階では、絞り込み条件の処理をデータベース側に寄せる改修が最初の一手になる。作り直しではなく、同じ構成のまま部品を強化する形で育てられる
- 検索結果の質は商品写真と説明文の質に比例する。実運用では商品撮影の統一が投資対効果の高いポイント

## 留意点

- 意味での検索は「近いものを並べる」仕組みであり、キーワード完全一致のような「絶対にこれ」という保証はない。型番検索など厳密な検索は従来型を併用するのが適切
- 商品情報の更新から検索への反映まで数分の時差がある（デモ用途では支障ない）
